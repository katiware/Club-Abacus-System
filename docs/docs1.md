a# 部費管理アプリ 要件定義書（フェーズ1・2完了時点）

**※会計担当者のファイル管理**
年度 → 提出/未提出 → 月 → 項目別

## 1. システム概要と目的
- **目的:** 部費（課外活動育成費）の残高や使途を透明化し、部員全員が現状を把握できるようにする。
- **アーキテクチャ方針:**
  - **Webアプリケーション:** 経費申請の入力、証憑（領収書等）のアップロード、会計担当による承認・管理など、複雑な操作を行うメインシステム。

## 2. ワークフロー定義
大学の規定に基づき、「立替払い（基本）」と「事前出金」の2つのフローを定義する。
※本システムは部内の「内部申請・承認」をデジタル化するものであり、大学への最終的な出金申請（UNIPA経由）および原本提出は、従来通り会計担当が手動で行う。

### 2.1 フローA：立替払いによる出金（原則）
部員が先に代金を支払い、後日大学から出金される標準的なフロー。
1. **ログイン**: 部員だけログインできるよう
2. **内部申請 (Web)**: 一般部員がWebアプリから経費情報（金額、使途など）を入力する。また、この際、実店舗なのかWeb購入なのかも分類。
3. **内部承認 (Web)**: 会計担当がWebアプリ上で申請情報（金額、使途など）を確認し、承認する。
   ※この時、部内投票を始めて、採決を取ることもできる。代表者のみの投票 or もしくは全員で選択、どちらか選べるように。
4. **書類アップロード**: 必要書類をアップロードする。(Webの場合のみ)
5. **内部承認 (Web)**: 会計担当がWebアプリ上で領収書内容（宛名、日付、金額、明細など）を確認し、承認する。
6. **大学へ申請 (手動)**: 会計担当が承認済みデータを元に公式申請書類を作成し、毎月5日の期限までに近大UNIPAへ提出、原本を窓口へ提出する。
7. **精算・記録 (手動・Web)**: 毎月27日前後の振込日に大学から入金後、会計担当が現金を引き出し部員に手渡しする。その際、立替金受け渡しリストにサインをもらい、Webアプリ上のステータスを「精算済」に更新する。

### 2.2 フローB：事前出金による支払い
購入前に大学から概算額を受け取り、支払い完了後に領収書を提出するフロー。
1. **ログイン**: 部員だけログインできる
2. **見積申請 (Web)**: 一般部員がWebアプリから「事前出金」を選択する
3. **書類アップロード**: 見積書または請求書のPDFをアップロードする。
4. **内部承認・大学申請 (Web・手動)**: 会計担当が見積書を承認し、大学へ公式の出金申請を行う。※この時、部内投票を始めて、採決を取ることもできる
5. **出金・受け渡し (手動)**: 大学からの入金後、会計担当が部員へ現金を渡す。
6. **支払い・領収書提出 (Web)**: 部員が支払いを完了させた旨を、Webアプリ上の同申請画面から操作する。
7. **必要書類アップロード**: 必要書類を追加アップロードする（出金申請月の翌月20日が提出期限）。
8. **内部承認 (Web)**: 会計担当がWebアプリ上で領収書内容（宛名、日付、金額、明細など）を確認し、承認する。
9. **大学へ報告 (手動)**: 会計担当が領収書を確認し、大学へ会計報告を行う（報告がない場合は次の出金が不可となる）。

| 手順 | アクション (誰が・どこで・何をするか) | システムの状態 (ステータス) |
| :--- | :--- | :--- |
| **1. 購入申請** | **一般部員**がWebアプリから「購入予定の内容（金額、使途、**購入方法: Web/実店舗**）」を入力し、申請を出す。 | PENDING_APPROVAL (承認待ち) |
| **2. 内部承認** | **会計担当**がWebアプリ上で申請内容を確認し、購入の許可（承認）を出す。 | APPROVED (購入許可済) |
| **3. 購入実行** | **一般部員**が実際に商品を購入し、領収書を受け取る。 | (ステータス変更なし) |
| **4. 証憑提出** | **【Web購入の場合】** **一般部員**がWebアプリ上で領収書データ（画像/PDF）をアップロードする。<br>**【実店舗購入の場合】** 画像のアップロードは不要。**一般部員**が紙の領収書を会計担当に手渡しする。 | WAITING_CONFIRMATION (最終確認待ち) |
| **5. 最終確認** | **会計担当**が提出された画像データ（Webの場合）または原本（実店舗の場合）を確認し、システム上で完了操作を行う。 | COMPLETED (大学申請・精算準備完了) |

※将来的にはフローAとBともに申請書のフォルダ分別、申請書の自動作成を想定

### 2.3 フローC：定期の支払い

| 手順 | アクション (誰が・どこで・何をするか) | システムの状態 (ステータス) |
| :--- | :--- | :--- |
| **1. 初回登録申請** | **一般部員**がWebアプリから「定期支払い」として新規申請。支払い頻度（月次/年次）と初回支払予定日を設定する。 | PENDING_APPROVAL (承認待ち) |
| **2. 初回承認** | **会計担当**が内容を確認し、継続購入を許可する。親となるテンプレートデータが作成される。 | APPROVED (購入許可済) |
| **3. データ自動生成** | システムが設定された頻度・日付に基づき、自動的に当月/当年提出用の「立替精算データ」を生成する。 | WAITING_CONFIRMATION (証憑提出待ち) |
| **4. 証憑提出** | **一般部員**がWebアプリ上で当月/当年分の領収書データをアップロードし、実際の支払い金額を上書き入力する。 | WAITING_CONFIRMATION (最終確認待ち) |
| **5. 最終確認・精算** | 以降はフローAと同様。**会計担当**が領収書を確認し、システム上で完了操作を行ったのち、大学へ申請・精算を行う。 | COMPLETED (完了) |

## 3. アプリケーション機能要件

### 3.1 Webアプリ機能（共通機能）
- **ログイン機能**: Googleアカウントでのログイン
- **ダッシュボード**: 現在の総残高、カテゴリ別支出グラフなどの可視化。
- **経費申請フォーム**: 日付、金額、支払先、使途カテゴリ、用途詳細、備考欄の入力。その後、申請内容に不備があった場合は変更も可能(管理者ログに追記)
- **申請タイプ選択**: 「立替払い（領収書）」か「事前出金（見積書/請求書）」かの選択。また、書類タイプ(Webなのか紙なのか)もここで選択
- **証憑アップロード**: 領収書や見積書の画像（またはPDF等）のアップロード機能。また、画像の差し替えもできるようにする。(管理者ログに追記)
- **追加アップロード機能**: 事前出金で申請したデータに対し、後日「領収書」を追加提出する機能。
- **ステータス確認**: 自身の申請が「承認待ち」「大学へ申請中」「領収書提出待ち」「精算済」等のどの段階にあるかの確認。
- **未報告アラート**: 事前出金の領収書提出期限（翌月20日）が迫っている未提出データへの警告表示。
- **金種計算機能**: 「一人ひとりに渡す分」で、必要な紙幣・硬貨の枚数を計算する。全体の合計金額から計算するのではなく、個人ごとに渡す金額に合わせて必要な紙幣や硬貨の枚数を割り出す。

### 3.2 Webアプリ機能（会計・管理者のみ可能）
- **高額申請アラート**: 5万円以上（単価）の物品購入時に、事前の備品購入申請書提出が必要である旨の警告表示。
- **台帳管理・ステータス変更**: 全メンバーの申請履歴閲覧、申請の「承認 / 差し戻し（コメント付与）」、および進行状況に応じたステータスの手動変更機能、また申請の強制削除なども追加。
- **操作ログ管理**: 申請内容の変更などの履歴を閲覧
- **年度リセット機能**: 単年度予算制（4月1日〜翌年3月31日）に対応するための、年度ごとのデータ区切り機能。
- **部員管理**: 部員名簿の追加、アカウントの停止・削除など
- *(※Excel/CSVエクスポート機能は初期開発要件から除外とする。今後実装したい)*

## 4. 機能の詳細化（API・処理の細分化）
追加された要件を実現するために、システムが内部でどのようなAPI（通信窓口）や処理を持つべきかを整理します。

### 4.1 認証・ユーザー管理 API
- **POST `/api/auth/login` (Googleログイン処理)**:
  - フロントエンドからGoogleの認証トークンを受け取ります。
  - バックエンドで `Users` テーブルを検索し、該当のメールアドレスが登録されており、かつ有効状態（`is_active = true`）である場合のみアクセストークンを発行します。未登録の場合は「未認可エラー」を返します。
- **GET, POST, PUT, DELETE `/api/admin/users` (部員管理処理)**:
  - 管理者のみが実行可能なAPIです。部員の追加、情報更新、および論理削除（`deleted_at` へのタイムスタンプ記録）を行います。

### 4.2 経費申請・ワークフロー進行 API
下書き状態を廃止し、申請と承認、その後のファイル提出を管理します。
- **POST `/api/expenses` (購入申請・見積申請)**:
  - 金額、使途、購入方法（`WEB` または `PHYSICAL`）、申請タイプ（`REIMBURSEMENT` または `ADVANCE`）などのテキストデータを送信します。
  - この時点のステータスは `PENDING_APPROVAL`（購入承認待ち）として登録されます。
- **PUT `/api/expenses/{id}/status` (ステータス変更)**:
  - 管理者が操作するAPIです。
  - 「承認」を実行すると、ステータスが `APPROVED`（購入/証憑提出待ち）に進みます。
  - 実店舗購入（`PHYSICAL`）の場合、部員からの画像アップロードがないため、管理者が紙の領収書を受け取ったタイミングで、このAPIを使ってステータスを `WAITING_CONFIRMATION`（最終確認待ち）や `COMPLETED`（完了）へ手動で進めます。

### 4.3 画像・ファイル管理 API
- **POST `/api/expenses/{id}/images` (証憑アップロード・差し替え)**:
  - 対象の経費データが `APPROVED`（購入許可済）であり、かつ購入方法が `WEB` の場合のみ許可されるAPIです。
  - 受け取った画像ファイルをクラウドストレージ（AWS S3等）へ保存し、取得したURLをデータベースの `receipt_url` または `estimate_url` に記録します。
  - ステータスを自動的に `WAITING_CONFIRMATION`（最終確認待ち）へ進めます。
  - 画像の差し替えが行われた場合は、`AuditLogs` テーブルに「画像の差し替え」という操作履歴を自動記録します。
