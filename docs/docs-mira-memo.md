# 開発メモ (mira-memo)

## 1. 決まったこと・仕様方針

### 1.1 UI・プラットフォーム
- スマホとPCの両方で閲覧可能とする
- Discord上で残高や履歴などを確認できるようにする
- 申請方法がわかるページ(PDF)を用意する(ユーザ向け)

### 1.2 経費申請・フロー
- **事前出金**: ホテルなど金額が高い場合は事前出金も可能
- **購入方法の分類**: 申請を「実店舗購入」「Amazon購入」「その他Web購入」に分ける
- **証憑管理**:
  - 画像は形式などが合っているか確認するためのもの
  - 領収書の内容が不適当な場合、申請オブジェクトとして持ってステータスを管理する
  - 紙のとき（実店舗）は学校側にアップロードする必要はない
  - Amazon購入の場合は、領収書と適格請求書（または見積書）の提出が必要。その旨を通知する
  - 過去のデータ（領収書など）をどれぐらい保存するかは今後検討
- **金額・ステータス管理**:
  - 領収書の提出段階で金額変更もできるようにする
  - 申請者から編集が行われた場合、管理者の確認が必要とする（承認のフローに戻す）
  - 長期間同じステータスのままの場合、通知する
  - ステータス変更をまとめてできるようにする（大学への申請のときなど）
- **定期支払い**:
  - 31日を指定した場合、31日が存在しない月があるため「月末」と指定できるようにする
  - 定期払いで何月分の申請かを保存する（Model変更）
  - 担当者が変わった場合に担当者を変更できるようにする
  - 年度をまたいでも自動継続する

### 1.3 ユーザー・権限管理
- 現部員以外はログインできなくする
- アカウント登録は管理者が行う（Excelの名簿を使って一括登録等）
- ユーザ管理画面で、ロール割り当てと権限割り当て（特別な場合）が別で必要
- Userの `discordId` はNull非許容にする（Model変更）

### 1.4 通知タイミング (Bot)
- 新規申請時 ➔ 管理者へ通知
- 申請承諾時 ➔ 申請者へ通知
- 1週間以上放置 ➔ 催促通知
- 大学への申請リマインド ➔ 会計担当へ通知
- 立替えた人に部費を渡すリマインド ➔ 会計担当へ通知

### 1.5 予算・残高管理
- **残高減少のタイミング**: アプリ上の残高は「申請時」のタイミングで減る
- **予算枠**: Excelの予算額は年度はじめに入力する
- **裏金・プール金（予算外）の扱い**: アマギフなどの部の予算外のお金は管理者のみに表示し、ユーザ側の表記は自腹など（オブラートに包む）
- **事前出金で差額が生じた場合の処理**:
  - 見積もりより少ない: 別のものを買う（その時足りない分はプールから出す）
  - 見積もりより費用が多い: プールから出すか、事務で申請する（凸る）
- **予算オーバー対策 (計算の分離)**:
  - 金額の計算を「申請未許可合計」「申請許可済み合計」「支出確定(大学へ申請済み)合計」に分ける
  - 「許可済み合計 ＋ 支出確定合計」の金額が予算を上回らないようにする
  - 「申請未許可 ＋ 許可済み ＋ 支払確定」の合計が予算を上回る場合は、管理者へ通知する（取捨選択のため）

### 1.6 その他資料
- 「大学の課外活動育成費（部費）マニュアル」を保存しても良いか ➔ `.gitignore` に入れて管理外とする

## 5. 【AI分析】既存要件・現在の実装との食い違い（Gap分析）

現在のソースコード（バックエンド・フロントエンド）や、これまでの設計ドキュメント(`docs1`〜`docs9`)と、本メモの内容を照らし合わせた結果、以下の実装上のギャップ（未反映・修正が必要な点）が見つかりました。

1. **`User` モデルの `DiscordId` Null許容設定**
   - **現状**: `backend/Models/User.cs` では `public string? DiscordId` とNull許容（オプショナル）になっています。
   - **対応**: メモの通り、必須（Null非許容）にするためにモデルの `?` を外し、DBマイグレーションが必要です。
2. **購入方法 (PurchaseMethod) の細分化**
   - **現状**: Enumおよびフロントエンド(`ExpenseForm.jsx`)では「Web購入(`WEB`)」と「実店舗購入(`STORE/PHYSICAL`)」の2択です。
   - **対応**: 「Amazon購入(`AMAZON`)」という3つ目のカテゴリを追加し、Amazon選択時は「見積書と適格請求書」の2ファイルを要求するUIロジックを追加する必要があります。
3. **定期支払い (Recurring) モデルの不足カラム**
   - **現状**: `ExpenseRequest.cs` には `IsRecurringTemplate` しかありません。
   - **対応**: メモにある「月末指定」「何月分の申請か (`target_period_start`)」を保存するためのカラムの追加と、二重生成防止の `UNIQUE` 制約が必要です。
4. **申請編集時のステータス巻き戻し**
   - **現状**: ステータス遷移の厳密なバリデーションルールは未実装です。
   - **対応**: 申請者が金額や領収書を変更した場合、自動的に `PENDING_APPROVAL` (承認待ち) に戻すバックエンドロジックをコントローラー/サービス層に実装する必要があります。
5. **残高計算ロジック（申請未許可分の即時減算）**
   - **現状**: `bot/cogs/budget.py` 等のモックでは単純な「総予算 - 支出済」になっています。
   - **対応**: バックエンドの残高計算APIで、「申請未許可 (Pending)」「許可済み (Approved)」「支出確定 (Completed)」を分けて集計し、UI上の残高はPendingの段階で減らすロジックを組む必要があります。
6. **ExpenseRequestモデルの肥大化改善**
   - **現状**: 一つのモデルにヘッダー情報が集中しています。
   - **対応**: 将来的に「申請基本情報」「購入メタデータ」「承認フロー情報」などでテーブル/クラスを分割するか、所有エンティティとして整理するリファクタリングが推奨されます。
